# 开发工作流

## GVA Helper / MCP 约束

如果当前环境可用 GVA Helper 或其他项目专用 MCP 工具，开发前应优先使用它获取项目级建议、约束和示例，再落地具体实现。

## 推荐开发顺序

1. 先分析需求与接口
2. 先设计后端模型和请求结构
3. 再实现 Service 层业务逻辑
4. 再实现 API 层与 Router 层
5. 最后补齐 `initialize/`、插件入口或前端接入
6. 完成后进行联调与验证

## 前后端协作顺序

- 后端优先给出稳定接口
- 前端可基于 Mock 或 Swagger 并行开发
- 联调时以后端真实接口契约为准

## 分支策略

- `main`: 主分支 / 生产分支
- `dev-X.Y.Z`: 版本开发分支（如 `dev-2.9.3`），日常开发与 PR 以当前版本开发分支为目标
- 功能分支应合入对应 `dev-X.Y.Z` 后清理；仓库另存有少量历史遗留分支（`v2.4.x`、`i18n` 等），不作为命名参照

## 提交规范

建议使用语义化提交：

- `feat`
- `fix`
- `docs`
- `style`
- `refactor`
- `test`
- `chore`

推荐格式：`type(scope): description`

## 代码审查

代码审查使用 `dual-code-review` skill，集成两种互补能力并按性价比路由到三种场景：

| Agent | 名称 | 能力 | 底层技能 |
|---|---|---|---|
| Agent A | Atlas（擎天神·架构全局） | 架构、计划对齐、模块边界、生产就绪 | `requesting-code-review` |
| Agent B | Sentry（哨兵·行级细节） | 逐行 bug、安全、性能、边界 | `open-code-review`（ocr） |
| Agent C | Solomon（所罗门·睿智裁决） | 交叉验证、去重、裁决冲突、定级 | 独立子代理 |

| 场景 | 流程 | 成本 | 适用 |
|---|---|---|---|
| 场景 1 · 单路快速 | 只跑 Atlas 或 Sentry 一个 | 1× | 日常小改动、常规提交 |
| 场景 2 · 主审+复审 | 主跑一个，另一个二次复审 | 2× | 中等改动、跨 1-2 模块、存疑 |
| 场景 3 · 双路+仲裁 | Atlas + Sentry 并行 → Solomon 仲裁 | 3× | 大功能、合并 main 前、跨多模块 |

选择原则：改动 < 5 文件/单模块 → 场景 1；5-15 文件/跨 1-2 模块 → 场景 2；大功能/合并 main/跨多模块 → 场景 3。

要求：
- 多 agent 审查必须用**同一组 SHA**，保证可比
- 审查只读，不修改工作树
- 场景 3 的 Atlas+Sentry 必须**并行派发**（同一消息两个 task 调用）
- 审查发现的存量问题（历史脏数据/架构债）记入业务记忆或待办
